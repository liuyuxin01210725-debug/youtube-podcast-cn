# AI 随身听 MVP 设计

日期：2026-07-14

## 1. 产品决定

项目继续以“先解决自己的收听需求，顺带对外传播”为原则，不在第一版建设公开音频平台。

产品的长期定位是 **AI 随身听**：用户提供想了解的内容或主题，系统把 YouTube、网页、论文或文字转换成适合特定时间和场景收听的中文音频。

当前 MVP 只验证一个核心假设：

> 当生成质量足够好，并且音频会自动出现在微信里，用户是否会在开车、健身和走路时持续使用？

为控制范围，MVP 拆成两个顺序实施的项目：

1. **项目 A：Qwen3-TTS 音质升级**。在现有命令行和 Skill 中加入高质量语音模式，保留 EdgeTTS 作为稳定方案。
2. **项目 B：私人微信音频库**。生成完成后自动上传，只允许本人和少量邀请用户收听。

只有项目 A 通过真实音频 A/B 测试后，才进入项目 B。两个项目分别编写实施计划和验收。

## 2. 用户旅程

### 2.1 当前 MVP

1. 用户向 Codex 或 Claude Code 发送 YouTube 链接、文章、论文或文字。
2. 工具提取或读取内容，生成忠实、自然的中文听稿。
3. 工具使用用户选择的 TTS 后端合成完整 MP3。
4. 项目 B 完成后，工具自动上传 MP3 和元数据。
5. 用户打开微信小程序，在“我的音频”中直接播放。
6. 小程序支持后台播放和断点续播。

### 2.2 远期体验，不进入本次 MVP

用户可以说：“我开车 30 分钟，想听懂 AI Agent 最近的发展，不要太技术化。”系统先搜索已有音频；没有合适内容时再异步生成，并在完成后通知用户。

这项能力在有真实收听数据后再建设，当前不实现自然语言点播、自动检索生成、推荐算法或付费。

## 3. 项目 A：Qwen3-TTS 音质升级

### 3.1 范围

现有 EdgeTTS 能力必须继续工作。新增的 Qwen3-TTS 是可选择的“高质量模式”，不替换现有默认值，直到 A/B 测试证明它明显更好。

第一阶段支持两个后端：

- `edge`：当前免费、快速、稳定的默认后端。
- `qwen3-api`：调用阿里云百炼 Qwen3-TTS 非实时 API，适合长音频。

`qwen3-local` 只作为后续实验，不进入第一轮实现。原因是当前电脑可以尝试小模型，但官方路径主要围绕 CUDA；先用 API 验证音质价值，比先解决本地推理兼容性更有效。

### 3.2 命令和配置

命令行增加明确的 TTS 选项：

```bash
bash bin/tts-cn.sh transcript.md --tts edge
bash bin/tts-cn.sh transcript.md --tts qwen3-api
```

端到端 Skill 同样接受这项选择。没有指定时继续使用 `edge`，保证现有用户行为不变。

Qwen3-TTS 使用 `DASHSCOPE_API_KEY`。Key 从 macOS 钥匙串或环境变量读取，不写入命令参数、日志、缓存、仓库或小程序。现有 `podcast-cn-qwen` 钥匙串项目可以复用。

### 3.3 内部结构

把 `scripts/tts-cn.py` 当前直接调用 EdgeTTS 的代码拆成稳定接口：

```text
TTSBackend
├── EdgeTTSBackend
└── Qwen3APIBackend
```

后端只负责“给定文字、音色和输出位置，生成一个可解码的音频片段”。文本清理、说话人识别、切片、停顿、拼接、完整性验证和原子发布继续由公共流水线负责。

这样可以独立更换 TTS 服务，不影响翻译和音频拼接逻辑。

### 3.4 音色与表达

第一版不克隆原主播声音。主持人和嘉宾使用固定的中文内置音色映射，同一人物在整集内必须保持一致。

Qwen3-TTS 提供两个固定表达预设：

- `conversation`：自然聊天、语气有起伏、避免播音腔，适合访谈。
- `documentary`：平静、清楚、节奏稳定，适合论文、文章和单人讲解。

系统根据输入类型选择预设，用户也可以显式覆盖。表达预设是稳定配置，不对每个片段临时生成不同指令，避免整集声音漂移。

### 3.5 缓存和恢复

每个片段按以下信息生成缓存指纹：

- TTS 后端和模型
- 音色
- 表达预设
- 文本内容
- 影响音频结果的参数

已成功且能解码的片段持久化缓存。任务中断或接口限流后重跑，只补缺失片段。切换后端、模型、音色或表达预设时必须隔离旧缓存。

任何片段失败时，不发布残缺 MP3，也不静默混用 EdgeTTS 补齐 Qwen 音频。用户可以明确重试，或明确选择 EdgeTTS 重新生成整集。

### 3.6 日志

完成后只显示对用户有用的信息：

- 使用的 TTS 后端和模型
- 成功、失败、重试和缓存命中片段数
- 音频时长和生成耗时
- Qwen3 API 请求量；若接口能返回用量，则记录可计算的成本信息
- 最终 MP3 路径

日志不得出现 API Key、完整请求头或带鉴权参数的下载地址。

### 3.7 A/B 质量闸门

用同一批中文听稿制作盲听样本：

1. 两人访谈，重点检查人物区分和语气。
2. 含中英文专有名词的知识内容，重点检查发音。
3. 2 至 3 分钟单人讲解，重点检查长段节奏和疲劳感。

每个样本同时生成 EdgeTTS 和 Qwen3-TTS 版本。记录自然度、发音、人物一致性、节奏、生成时间和估算成本。

Qwen3-TTS 进入推荐模式的标准：用户在至少三个样本中的两个明确更愿意听 Qwen3 版本，并且没有严重漏读、错读、声音漂移或成本失控。否则保留为实验选项，EdgeTTS 继续默认。

### 3.8 项目 A 验收标准

- 原有 EdgeTTS 命令和测试全部通过。
- `--tts qwen3-api` 可以完成一段多人中文听稿的合成。
- 中断后重跑会复用成功片段，不重复产生对应费用。
- 任一片段失败时不会覆盖旧的完整 MP3。
- Key 不出现在仓库、进程参数和普通日志中。
- 完成三组真实盲听对比，并记录用户选择。

## 4. 项目 B：私人微信音频库

### 4.1 产品范围

第一版使用小程序开发版或体验版，只服务本人和少量邀请用户。它是个人工具的移动播放器，不是公开电台、有声读物平台或用户内容社区。

第一版所有 `enabled` 用户看到同一个由 owner 维护的私人音频库；每个人的播放进度相互隔离。它暂不支持“每个用户拥有自己的内容库”，避免过早引入内容分发和多租户逻辑。

包含：

- 微信登录和邀请名单
- “我的音频”列表
- 标题、主题、来源、时长和生成时间
- 标题和主题搜索
- 后台播放
- 断点续播
- 本地工具生成后的自动上传
- 上传失败后自动重试，不影响本地 MP3

不包含：

- 公共内容广场
- 评论、关注和分享社区
- 用户公开投稿
- AI 推荐算法
- 自然语言点播和缺失内容自动生成
- 付费、会员和额度
- 公开传播未经授权的完整翻译音频

### 4.2 系统结构

使用微信小程序、CloudBase 云函数、数据库和对象存储：

```text
本地转换工具
    │
    ├── 生成 MP3 和元数据
    │
    └── 调用受保护的上传接口
            │
            ├── 获取一次性上传凭证
            ├── 上传到私有对象存储
            └── 完成校验后写入音频记录
                         │
微信小程序 ── 微信登录 ─┴── 我的音频 / 播放 / 进度同步
```

本地上传器持有的上传令牌保存在 macOS 钥匙串。云端返回短期、一次性的上传凭证，本地不保存腾讯云长期密钥。小程序前端不包含 DeepSeek、DashScope 或云存储管理密钥。

### 4.3 数据模型

`users`：

- `openid`
- `role`：`owner` 或 `invited`
- `enabled`
- `created_at`

`episodes`：

- `id`
- `owner_id`
- `title`
- `topics`
- `source_type`：`youtube`、`web`、`paper` 或 `text`
- `source_url`
- `audio_object`
- `duration_seconds`
- `status`：`uploading`、`ready` 或 `failed`
- `rights_note`
- `created_at`

`playback_progress`：

- `user_id`
- `episode_id`
- `position_seconds`
- `completed`
- `updated_at`

数据库只在音频上传完成、校验通过后把记录标记为 `ready`。小程序只展示 `ready` 内容。

### 4.4 上传行为

音频生成成功后，本地工具执行幂等上传：

1. 计算 MP3 校验和，连同元数据请求上传任务。
2. 后端若已经存在同一校验和的完整音频，直接返回已有记录。
3. 否则返回一次性上传凭证。
4. 本地上传 MP3，并调用完成接口。
5. 后端校验文件大小、类型和必要元数据后标记为 `ready`。

网络失败不删除或移动本地 MP3。下次运行可以继续上传。自动上传可以在配置中关闭；关闭后，现有本地工作流完全不受影响。

### 4.5 播放体验

小程序首页直接显示最近音频，不设置营销落地页。点开音频即可播放，并支持：

- 锁屏或切到其他应用后的后台播放
- 15 秒前进和后退
- 0.8、1.0、1.2、1.5 和 2.0 倍速
- 进度自动保存
- 再次打开时从上次位置继续
- 上一集、下一集和简单播放队列

移动网络下先播放，不要求整集下载完成。无法播放时提供明确重试，并保留上次进度。

### 4.6 权限和内容边界

- 未在邀请名单中的账号不能读取音频列表或音频地址。
- `enabled` 用户可以读取 owner 私人库中的 `ready` 音频，但只能读取和修改自己的播放进度。
- 音频对象默认私有，播放链接短期有效。
- 每条音频保留原始来源和 `rights_note`，为后续公开传播审核留痕。
- 当前版本不提供公共分享链接。
- 如果未来进入公开电台、有声读物或付费内容，必须单独完成版权授权、微信类目和所需资质评估，不能沿用私人 MVP 的假设直接上线。

### 4.7 项目 B 验收标准

- 一条生成成功的 MP3 可以自动上传，并在两分钟内出现在“我的音频”。
- 同一文件重复执行不会创建重复音频。
- 未授权微信账号不能读取列表或播放地址。
- iPhone 真机可以后台播放，并在重新进入后从保存位置继续。
- 网络中断后本地 MP3 保留，恢复后可重试上传。
- 旧的本地生成命令在未配置小程序时继续正常工作。

## 5. 测试策略

项目 A：

- 单元测试覆盖后端选择、音色映射、表达预设、缓存指纹和失败保护。
- 使用伪造 API 响应测试限流、超时、无效音频和重试，普通测试不产生真实费用。
- 使用一个短样本完成真实 API 冒烟测试。
- 运行现有完整测试，确保 EdgeTTS 回归通过。

项目 B：

- 后端测试覆盖邀请权限、一次性上传凭证、幂等上传、校验和与状态变化。
- 小程序测试覆盖空列表、加载、失败、播放和进度恢复状态。
- 使用 iPhone 真机验证后台播放、锁屏控制和移动网络恢复。
- 使用未授权微信账号进行访问测试。

## 6. 实施顺序和决策闸门

1. 为项目 A 编写详细实施计划。
2. 实现 Qwen3-TTS API 后端和持久缓存。
3. 运行自动测试和三组真实 A/B 样本。
4. 用户决定 Qwen3 是否成为推荐模式。
5. 为项目 B 单独编写详细实施计划。
6. 建设上传后端和最小小程序播放器。
7. 由本人和少量邀请用户连续使用两周。

进入后续自然语言点播或推荐功能前，至少观察：每周收听次数、开始播放率、完成率、跳过位置、重复播放和主动搜索。没有真实使用数据时，不建设推荐算法。

## 7. 成功定义

这个 MVP 的成功不是“上线了一个小程序”，而是：

- 用户每周至少三次把生成音频用于开车、健身或走路。
- 自动进入微信后，用户不再需要手动寻找、传输和管理 MP3。
- 音质足以让用户愿意连续听完，而不是只觉得技术上能播放。
- 少量邀请用户中出现重复使用，而不是只体验一次。

如果这些行为没有出现，优先修复内容质量、音质和导入摩擦，不增加公开平台、推荐或付费功能。
